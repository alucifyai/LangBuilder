# Story 4.2: Token Scope Enforcement - DETAILED REVIEW

## Status

**Partially Implemented - Needs Extension**

## Story

**As a** Developer,
**I want** API tokens scoped to roles and resources,
**so that** tokens cannot be misused.

## Acceptance Criteria

**@AC1**: Scoped token access
- When Pat creates a token with actions ["read"] scoped to PRJ1
- Then the token only works for reading flows in PRJ1
- And access outside PRJ1 is denied

## Context Analysis - What Exists

### 1. Regular API Keys (User Tokens)

**File**: `src/backend/base/langflow/services/database/models/api_key/model.py`

**Current Model**:
```python
class ApiKey:
    id: UUID
    api_key: str
    user_id: UUID  # Links to user
    name: str
    is_active: bool
    last_used_at: datetime
    total_uses: int
```

**Status**: ❌ **NO scope enforcement**
- Token inherits ALL user permissions
- Cannot restrict to specific project/workspace
- Cannot limit to specific actions

### 2. Service Account Tokens

**File**: `src/backend/base/langflow/services/database/models/service_account/model.py`

**Current Model**:
```python
class APIToken:
    id: str
    service_account_id: str
    token_hash: str
    scopes: list[str]  # ⚠️ Permission-level scopes only
    expires_at: datetime | None
    is_active: bool
    # ... usage tracking fields
```

**Scopes Available** (from `TokenScope` enum):
- `read`, `write`, `admin`
- `flows:read`, `flows:write`
- `projects:read`, `projects:write`

**Status**: ⚠️ **Partial implementation**
- ✅ Has permission-level scopes (what actions)
- ❌ Missing resource-level scopes (which resources)
- Cannot restrict to "Project=PRJ1 only"

## Gap Analysis

### What's Missing for Full PRD Compliance

The PRD requires: **"token with actions ["read"] scoped to PRJ1"**

Current implementation: **"token with scopes ["flows:read"]"** (works globally)

**Missing**:
1. Resource scope binding (Workspace, Project, Flow, etc.)
2. Scope validation during token authentication
3. Integration with existing Grant/Permission system

### Required Changes

#### 1. Extend APIToken Model

Add resource scope fields:
```python
class APIToken(SQLModel, table=True):
    # Existing fields...
    scopes: list[str]  # Keep for permissions
    
    # NEW: Resource scope restriction
    scope_type: str | None  # "Workspace", "Project", "Flow", etc.
    scope_id: str | None    # The actual resource ID
```

#### 2. Update Token Creation API

Allow specifying resource scope:
```python
class TokenCreateRequest(BaseModel):
    name: str
    scopes: list[str]  # Permission scopes: ["read", "write"]
    scope_type: str | None  # Resource scope: "Project"
    scope_id: str | None    # Resource ID: "PRJ1"
```

#### 3. Token Authentication Middleware

Add scope validation:
```python
async def authenticate_token(token: str, resource_type: str, resource_id: str):
    api_token = await get_token(token)
    
    # Check if token is restricted to a scope
    if api_token.scope_type and api_token.scope_id:
        # Validate request is within token's scope
        if resource_type != api_token.scope_type or resource_id != api_token.scope_id:
            raise PermissionDenied("Token scope violation")
    
    # Check permission scopes
    if required_permission not in api_token.scopes:
        raise PermissionDenied("Insufficient permissions")
```

## Risk Assessment

**Complexity**: Medium
- Models already exist, just need extension
- Authentication middleware already validates permissions
- Scope checking is additive (won't break existing tokens)

**Breaking Changes**: None
- Existing tokens without scope_type/scope_id work globally (current behavior)
- Only new tokens with explicit scopes are restricted

**Security Impact**: High
- Reduces token blast radius
- Prevents token misuse across projects
- Aligns with least-privilege principle

## Current vs Target State

### Current State
```
User creates token → Token has permission scopes → Works globally
Example: Token with ["read"] can read ANY project
```

### Target State (PRD Compliant)
```
User creates token → Token has permissions + resource scope → Works only in scope
Example: Token with ["read"] scoped to PRJ1 → Can ONLY read in PRJ1
```
